# hum1izer

Проверяет прозу, комментарии в коде и сообщения коммитов на канцелярит,
штампы и следы генерации. Не переписывает текст сам: показывает находки и
говорит, что с каждой делать. Переписываешь ты.

## Когда браться

- «сделай комментарии человечнее», «почисти комментарии», «убери AI-слоп»
- ревью текста, статьи, README, changelog на штампы и канцелярит
- проверка сообщений коммитов перед пушем
- после генерации кода моделью: сгенерированные комментарии почти всегда
  пересказывают код и пишутся учебным тоном

## Цикл правки

```bash
hum1izer --code --format jsonl --limit 20 ./src
```

Одна строка JSON на блок, самые грязные первыми. В stderr идёт
`remaining=N shown=N findings=N`.

```json
{"id":"src/a.ts:5-14","file":"src/a.ts","start":5,"end":14,"lang":"ts",
 "kind":"comment","score":7,
 "raw":"/**\n * This function is responsible for handling the request.\n */",
 "findings":[{"rule":"this function is responsible for","line":6,"hard":false,
              "fix":"Скажи, почему так сделано, а не что делает строка ниже"}]}
```

1. Прочитай строку. `raw` - исходный текст байт-в-байт, вместе с `//` и `/* */`.
2. Перепиши блок целиком с учётом всех `findings`.
3. Замени в файле точным совпадением по `raw`. Номера строк после первой же
   правки съезжают, поэтому опирайся на `raw`, а не на `start`/`end`.
4. Запусти проверку снова. Повторяй, пока `remaining` падает.

Останавливайся, когда `remaining` дошёл до нуля или не изменился два прохода
подряд. Во втором случае покажи, что осталось, и объясни почему: часть находок
это ложные срабатывания, их надо глушить в правилах, а не править текст.

## Как править комментарий

- Одна-две строки, это значение по умолчанию у `--max-lines`. Не влезает -
  значит, комментарий не нужен или нужен рефакторинг кода.
- Комментарий отвечает на «почему», код отвечает на «что». `// увеличиваем i`
  не нужен, `// индекс с единицы: API нумерует страницы с 1` нужен.
- Пересказ имени функции удаляй, а не переписывай.
- Закомментированный код удаляй: история живёт в git.
- Не знаешь, зачем код - удаляй комментарий, но не выдумывай причину.
  Выдуманное объяснение хуже отсутствующего.
- Баннеры из `=====` удаляй, порядок наводи файлами и функциями.
- `TODO` без владельца: добавь ссылку на задачу или имя, либо удали.
- Правь только комментарии. Код не трогай.

Не трогай никогда: лицензионные шапки и SPDX, `//go:generate`, `//go:embed`,
`//nolint`, `// Code generated ... DO NOT EDIT`, `eslint-disable`,
`@ts-expect-error`, прагмы компилятора, ссылки на задачи и коммиты.

## Настройки проекта

Рядом с кодом может лежать `.hum1izer.yaml` - он ищется от проверяемого каталога
вверх до корня. Там живут предел длины комментария, языки, исключения и
отключённые правила. Уважай его: если правило отключено в проекте, значит для
этого проекта оно норма.

```bash
hum1izer init          # создать файл настроек, вписав найденные языки
hum1izer init --print  # посмотреть, ничего не записывая
```

Если находка явно ложная и повторяется по всему проекту, предложи не правку
текста, а строку в `rules.disable` - имя берётся прямо из отчёта.

## Прочие режимы

```bash
hum1izer текст.md                  # русская проза, отчёт с рекомендациями
hum1izer --lang en post.md         # английский набор правил
hum1izer --code --commits 50 .     # плюс последние 50 сообщений коммитов
hum1izer --code --max-lines 12 .   # мягче: длинным считать блок от 13 строк
hum1izer --code --quiet .          # одна строка, годится для CI
```

Код возврата: `0` чисто, `1` есть жёсткие находки, `2` ошибка.

## Чего инструмент не умеет

Он работает регулярками и арифметикой. Смысловой пересказ, ирония, пустая
образность им не ловятся - это на тебе. И наоборот: находка не приговор.
Если комментарий по делу, а правило сработало зря, оставь как есть и скажи об
этом, вместо того чтобы портить текст ради нулевого счётчика.

# Методика

Как был сделан замер формы кода: 30 корпусов, 7 языков, ~362 тысячи функций.
Здесь то, что нужно, чтобы повторить его на своих репозиториях и не наступить
на грабли, на которые наступили мы.

## Что меряем

На каждую функцию четыре величины:

| величина | как считается | зачем |
|---|---|---|
| глубина вложенности | максимум уровней `if`/`for`/`while`/`switch`/`try` внутри тела | единственная, что держится через языки и десятилетия |
| длина | значащие строки: без пустых и без строк, где только комментарий | где расходится машинный код |
| цикломатика | 1 + число ветвлений, `&&` и `\|\|` считаются | для сверки с линтерами, порогом не годится |
| число параметров | именованных узлов в списке параметров | сопутствующая |

Дальше по корпусу берутся персентили (p50, p90, p95, p99) и доли нарушителей
порога. Персентили устойчивее среднего: одна функция на тысячу строк не должна
двигать оценку всего репозитория.

## Порядок работы

1. **Сверить счётчик с эталоном.** Прежде чем верить цифрам по новому языку,
   прогнать по языку, где есть независимая реализация. Мы сверяли `tree-sitter`
   с `go/ast`: 328 функций в обоих, тот же топ по массе, расхождение
   цикломатики в пределах `+-3`.
2. **Замерить долю ошибок разбора** (`ERR=1`). Если она заметная, все
   последующие числа - о том подмножестве, которое разобралось.
3. **Считать персентили и доли** (`STATS=1`).
4. **Сравнивать только внутри языка.** Java даёт 45-57% функций короче трёх
   строк, C - 0.8-4.4%. Межъязыковое сравнение этих долей бессмысленно.
5. **Проверять на ряде по годам** (`years.sh`), если у репозитория есть
   история. Величина, которая скачет год от года, порогом быть не может.

## Ловушки

**Препроцессор C.** `tree-sitter` спотыкается на `#if` внутри тела функции:
разбор разваливается, и функция «съедает» остаток файла. `winWrite` в
`sqlite3.c` намерилась в 19703 строки при настоящих 104. Доля битых файлов:
sqlite 75%, linux/fs 54.6%, coreutils 36.2%, PostgreSQL 56.8%. Функции с
узлами ERROR внутри надо отбрасывать - теряется 8-34% выборки, и потеря не
случайна: выбывают места с самым плотным препроцессором, а они обычно и самые
запутанные. Java, Go и Rust разбираются с нулём ошибок.

**Шаг отступа.** Если считать глубину по отступам, шаг файла надо брать модой
разниц между уровнями, а не минимумом. Выравнивание продолжений строки даёт
разрывы в один-два пробела, минимум ловит их и делит на единицу: на одном из
проверочных репозиториев наивная версия выдала `depth>4` = 13.3% вместо 0.0%,
ошибка в сорок раз.

**Отступ завышает хвост.** Даже с правильным шагом доля нарушителей выходит
примерно вдвое выше, чем по разбору дерева: gofmt даёт `switch` два уровня
отступа там, где дерево видит один. Медиана, p90 и p95 при этом совпадают.
Поэтому порог по отступам - 5, по дереву - 4.

**Физические строки против значащих.** Считать надо значащие: длинная функция
несёт больше комментариев, и на физических строках её вес растёт быстрее
остальных. На наших данных разница вышла в третьем знаке, но проверять стоит.

**Смешанные языки в одном репозитории.** Go плюс TypeScript в одном дереве -
короткие стрелочные функции фронтенда тянут медиану вниз. Замерять по
расширению отдельно: передать `probe` файл со списком путей.

**Разрез по дате появления файла ничего не показывает.** Мы пробовали делить
файлы на созданные до и после появления `AGENTS.md` в репозитории. В Intabia
Platform код после оказался хуже, в `tenniarb` - лучше, направления
противоположные. Видно и почему: из старых файлов `tenniarb` дожили 42 из 103,
и выжившие это самые правленые, а новый файл почти всегда проще старого
независимо от того, кто его писал.

## Чего эти метрики не умеют

**Отличать машинный код от человеческого.** Проверено на репозиториях, где
авторы сами заявляют «100% AI-generated»: глубина не различает вовсе (`slopos`
0.3% против 0.1-0.4% у tokio и ripgrep), различает только длина функций (p95
45-50 против 29-34). Глубина - метрика читаемости, а не происхождения.

**Заменять линтер проекта.** Если в репозитории настроены `cyclop`, `funlen`
или `sonarjs/cognitive-complexity`, его числа главнее: команда уже приняла
решение, и мерить её код против внешнего порога - шум.

**Служить целью.** Любая из этих величин, поставленная целью, перестаёт быть
измерением - ровно как пишет автор исходного поста про LOC.

## Оговорки про выборку

Заявления авторов о происхождении кода не проверены. Маленькие проекты (200-400
функций) дают шумные доли. Тип проекта - сильный конфаундинг: в `go/src/go`
много методов-однострочников для узлов AST, в CLI их взяться неоткуда.
